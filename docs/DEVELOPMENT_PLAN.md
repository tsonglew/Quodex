# QuotaPal Android 开发计划

更新日期：2026-10-10（Asia/Shanghai）。状态：开发进行中，实时记录见 [开发进度](PROGRESS.md)。

QuotaPal 首版面向 Android，参考 Nowdex 的额度速览体验，先支持 Codex 单账号和桌面小组件。发布顺序为先自用 APK、验证稳定性，再公开发布。用户应能在桌面判断还有多少额度、何时重置，以及数据最后更新于何时。

本计划、[开发与验收 checklist](DEVELOPMENT_CHECKLIST.md) 和 GitHub milestones 共同记录后续工作。实现与验证状态以 checklist 和开发进度中的证据为准。

## 接入前提

首个里程碑必须验证手机能否独立、持续获取真实额度，再确定正式开发排期。

- OpenAI 提供 `account/rateLimits/read`，但它属于 Codex App Server 的 RPC 接口，不能直接当作供 Android 调用的公网 REST API。[Codex App Server 文档](https://learn.chatgpt.com/docs/app-server)
- 官方已有 Sign in with ChatGPT 流程；登录成功不等于获得读取账号额度的权限。现有开源接入文档主要描述身份认证和使用订阅进行模型请求，尚不足以确认独立 Android 额度监控的完整接入路径。[接入概览](https://developers.openai.com/siwc/token-sharing-open-source)、[授权流程](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)
- 验证客户端适用范围、实际权限、额度读取、续期、撤销和账号／工作区映射，不把身份登录或一次成功请求作为全部接入已完成的证据。
- 应用行为限定为监控；若凭据权限更广，应如实说明，不能称为只读凭据。
- 若只能依赖未稳定接口，应记录兼容性、维护成本及公开发布条件。若必须通过电脑桥接，会改变手机独立查看的体验，需要重新评估范围与工期。

M0 的通过条件是可复现的接入结论、脱敏真实数据样本及限制清单。已完成一次真实额度只读探测，具体证据与未验收项见 [Codex 接入验证](CODEX_INTEGRATION.md)。

## 对标与产品范围

Nowdex 的核心体验包括额度、重置时间和小组件，同时提供多服务、多账号、同步及用量分析。其 Codex 说明指出，会话窗口仅在账号返回相应数据时显示。QuotaPal 首版先对齐核心体验，不预设所有账号都有两个额度窗口。[Nowdex 官网](https://nowdex.app/)

| 能力 | 自用 MVP | 公开首版或后续 |
| --- | --- | --- |
| 服务与账号 | Codex，单账号 | 首次公开发布仍可保持单账号 |
| 额度总览 | 已用／剩余、额度窗口、重置时间、更新时间 | 扩展账号支持的额外额度信息 |
| 桌面小组件 | 紧凑版、宽版，支持缩放 | 更多布局与个性化 |
| 数据刷新 | 手动刷新、后台尽力刷新、缓存 | 根据实测优化 |
| 账号管理 | 连接、重新连接、退出、清除数据 | 多账号放到下一版本 |
| 外观 | 中文、系统浅色／深色 | 英文、独立主题设置 |
| 通知 | 暂缓 | 低额度提醒、确认重置后的提醒 |
| 历史与费用 | 暂缓 | 单独验证数据来源后再做 |
| 多服务、跨设备同步 | 暂缓 | 后续扩展 |
| 聊天、执行任务、购买额度 | 不纳入当前计划 | 另立需求 |

额度百分比、token 数量和实际账单是不同指标，不能用百分比反推 token 或费用。API Key 计费与 ChatGPT 订阅用量应明确区分。[Codex 认证与计费说明](https://learn.chatgpt.com/docs/auth)

## 界面与用户流程

| 界面 | 主要内容 | 完成条件 |
| --- | --- | --- |
| 首次连接 | 用途说明、连接账号、授权结果、首次获取 | 成功进入额度页；失败可重试 |
| 额度首页 | 账号、各窗口百分比、重置时间、刷新状态 | 能直接判断剩余额度与数据新鲜度 |
| 小组件配置 | 布局预览、显示已用／剩余、添加引导 | 添加后立即显示缓存或明确的空状态 |
| 设置与诊断 | 刷新间隔、连接状态、重新连接、退出、帮助 | 能处理断网、过期和后台延迟 |

主要流程为连接账号、获取真实额度、添加小组件、日常桌面查看，以及异常时进入 App 恢复。

首次获取失败必须有可理解的原因与重试入口。日常查看以剩余额度和更新时间为主。低额度与登录失败应分别处理；故障时保留最后成功快照，退出或换号时清除旧账号数据。

## 技术方案

小组件和后台行为是核心功能，首版采用原生 Android，便于控制和验证。

| 部分 | 建议方案 | 目的 |
| --- | --- | --- |
| 语言与界面 | Kotlin、Jetpack Compose、Material 3 | 原生界面与主题适配 |
| 桌面小组件 | Jetpack Glance | 小组件布局、状态和交互 |
| 后台任务 | WorkManager | 管理周期同步与重试 |
| 网络请求 | OkHttp、Kotlin Serialization | 请求、解析、错误处理 |
| 数据缓存 | Room | 持久保存账号与最近成功快照 |
| 偏好设置 | DataStore | 刷新间隔、显示方式、组件配置 |
| 凭据保护 | Android Keystore 管理加密密钥 | 单独保存加密凭据 |
| 项目结构 | 单个 app 模块，按功能分包 | 控制首版复杂度 |

建议以 Android 10 及以上作为支持范围，开工时结合实际手机确认。`targetSdk` 和依赖版本在开工时按稳定版本及发布要求冻结。工程已按该方案创建；固定版本与构建方式见 README。

数据流为 Codex 数据适配器 → 统一数据仓库 → 本地快照 → App 与小组件。

前台刷新、后台刷新和小组件刷新共用同一套请求逻辑。多个小组件共享一次获取结果，避免重复轮询。Glance 与普通 Compose 的渲染能力不同，可以共享数据和设计规范，布局分别实现。[Glance 官方说明](https://developer.android.com/develop/ui/compose/glance/create-app-widget)

| 数据 | 需要保留的内容 |
| --- | --- |
| 账号 | 服务标识、账号标识、工作区标识（如适用）、显示名称 |
| 额度窗口 | 窗口标识、名称、时长、已用比例、重置时间 |
| 快照 | 最后成功获取时间、数据来源、所属账号 |
| 同步状态 | 最近尝试时间、错误类别、是否需要重新连接 |
| 小组件配置 | 实例 ID、绑定账号、显示模式、布局偏好 |

窗口数量、名称和时长以实际数据为准。缺失值显示暂不可用，不能当成 0%；倒计时结束不能在本地直接把额度补满。失败不得覆盖最后成功快照或更新成功时间。账号退出后，进行中的旧请求不得再写回数据。

## 小组件规格与刷新策略

| 布局 | 设计目标 | 展示内容 |
| --- | --- | --- |
| 紧凑版 | 约 2×2 格 | Codex、主要窗口剩余比例、重置时间、更新时间、刷新入口 |
| 宽版 | 约 4×2 格 | 主要额度窗口及进度条、各自重置时间、更新时间、刷新入口 |

格数是设计目标，实际按 Launcher 提供的尺寸适配。仅有一个窗口时自然展开；窗口更多时，小组件展示主要指标，App 提供完整详情。点击进入对应页面，刷新操作应有反馈。

WorkManager 周期任务最短为 15 分钟，但不保证准点执行；Doze 会推迟后台任务与网络访问，不能承诺实时额度或准点重置提醒。[周期任务限制](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest)、[Doze 官方说明](https://developer.android.com/training/monitoring-device-state/doze-standby)

刷新规则如下。

1. 默认后台目标间隔 30 分钟，可选 15、30、60 分钟；文案明确这是目标间隔。
2. 进入 App 时按缓存新鲜度决定是否刷新，用户可主动刷新。
3. 小组件始终展示最后成功更新时间，优先使用绝对时间；跨天时显示日期。
4. 刷新失败保留旧快照，并显示错误或数据较旧状态。
5. 合并同账号并发请求，连续点击刷新去重，防止旧响应覆盖新结果。
6. 网络错误退避重试；限流遵守服务端等待时间；认证失效提示重新连接。
7. 没有小组件且没有启用提醒时，可以停止周期同步。
8. 首版不依赖常驻前台服务或精确闹钟。
9. 后续通知基于成功获取后发现变化，不承诺变化或重置时立即通知。
10. 重置时间已到但尚未获取新数据时，提示待确认，不在本地恢复额度。

Android 15 起，强制停止应用会使小组件被系统禁用，重新启动应用后恢复。验收目标是恢复正常，不要求强停期间继续更新。[Android 15 行为变化](https://developer.android.com/about/versions/15/behavior-changes-all)

## 验证与交付要求

详细条目见 [开发与验收 checklist](DEVELOPMENT_CHECKLIST.md)。实施后组合数据解析与状态转换测试、账号和同步集成测试、小组件状态测试及真机 Launcher 验证。后台和真机验证重点检查延迟是否可解释、恢复是否可靠。

测试矩阵包含最低支持版本、Android 12、Android 15及届时最新稳定版，至少覆盖 Pixel/AOSP、Samsung、小米三类 Launcher，并优先加入实际自用手机。检查断网与恢复、凭据失效、限流、进程回收、重启、升级、时区与系统时间变化、大字体、浅深色和 TalkBack。

| 维度 | 验收目标 |
| --- | --- |
| 数据正确性 | 同一快照在 App 与组件中一致；缺失值不冒充零值 |
| 新鲜度 | 所有额度展示都有最后成功时间；失败不伪装成更新成功 |
| 性能 | 指定中档机缓存首屏 P95 ≤ 1 秒；正常环境下新快照落盘后组件更新 P95 ≤ 3 秒 |
| 请求控制 | 1 个和 3 个组件的周期请求量基本一致，无请求风暴 |
| 恢复能力 | 断网、凭据失效、进程回收、重启、升级均有通过记录 |
| 凭据保护 | 日志、备份、导出和组件状态中没有明文凭据 |
| 易用性 | 5 名目标用户中至少 4 名可独立连接、添加组件并读懂更新时间 |
| 发布质量 | 连续自用 7 天，无未解决的崩溃、账号混用或额度误显示问题 |

上述数字是项目验收目标，需要在测试设备确定后冻结，不属于平台保证。M4 安排 48 小时后台观察，记录请求数、实际刷新间隔、失败和耗电；公开发布前须完成连续自用及问题修复。

## 后续版本

下一版本可考虑同一服务多账号、独立的小组件显示设置、低额度提醒与确认重置后的提醒。再后续评估多服务、历史趋势、token 与费用统计、跨设备同步和更多布局。新增功能需要明确数据来源及维护成本，并重新拆分里程碑，避免扩大首版范围。

2026-10-10 用户确定首版公开渠道为 GitHub Releases APK，M5 按对应签名、版本、安装和资产交付规则验收。若后续收费，应重新确认接入方案的适用范围。先保持账号和数据适配边界清晰，不提前搭建自有账号系统、同步服务或复杂插件框架。

2026-10-10 新增后台引导范围：针对清理后台后停止更新的反馈，在设置页按手机品牌提供自启动、省电与任务锁定流程，明确强制停止边界。作为 M3–M4 的增量交付，验收 H01–H04 见 checklist，来源和设备差异见 [后台更新引导](BACKGROUND_GUIDE.md)。

2026-10-11 用户新增交付要求：每次 master 正式出包自动上传 GitHub Releases。已实现按运行号及 attempt 保存独立构建预发布，完整 CI、固定签名及资产验证为发布前置条件。该授权允许测试包公开下载；稳定版的真实账号、OEM、连续自用与性能／易用性验收目标保持不变。
