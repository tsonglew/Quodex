# 网络重试

alpha29 为额度查询、Token 统计、应用更新检查和 APK 下载补齐自动重试。登录授权、令牌交换和续期不增加自动重试。

| 操作 | 临时失败后的处理 |
| --- | --- |
| App 内额度与 Token 查询 | 每次操作最多尝试 3 次，通常等待 1 秒、2 秒；成功后才替换缓存。 |
| GitHub 更新检查 | 公开静态索引最多尝试 3 次；连接失败时备用 API 每页最多尝试 3 次。每个来源检查上限 60 秒，两者合计最多约 120 秒；失败保留已知版本。 |
| 用户发起的 APK 下载 | 最多尝试 3 次，显示等待与尝试次数；从原始 GitHub 下载地址重新取得重定向，重新下载、校验整个文件。 |
| 后台额度与 Token 任务 | WorkManager 每轮最多执行 3 次，采用 30 秒起的指数退避；单轮 HTTP 关闭上述内部重试。小组件点击先做一次有时限的即时请求，必要时交给后台任务。 |

网络中断、超时、HTTP 408／429／500／502／503／504 可重试。GitHub 的 403 仅在响应明确说明限流时重试。认证失效、无权限、其他不可重试状态、数据格式错误、TLS 证书错误、文件写入失败，以及 APK 地址、大小、哈希或签名校验失败，都直接结束并提示。

服务端提供 `Retry-After` 时，等待时间不短于该要求；GitHub 也读取限流重置时间。超过 30 秒的等待不占用前台操作，保留截止时间并结束本轮，等待后续任务或用户操作。额度和更新检查的截止时间写入本地设置；Token 和下载的额外截止时间目前保留于进程内。取消等待后，同进程的新操作仍遵守已收到的服务器截止时间。取消操作不会继续发请求，下载失败或取消会清理未完成文件。

更新检查仍默认按 12 小时目标周期运行，APK 下载仍需用户主动发起。下载重试从头开始，不做断点续传，因此可能增加下载流量。alpha33 的更新检查改为访问 raw.githubusercontent.com 的公开索引，不携带账号数据；不新增遥测。

验证覆盖恢复成功、次数上限、限流、取消、后台不叠加重试、下载截断后的重新取址及完整校验、缓存保留，以及重试提示与取消按钮。Android 测试使用合成响应，不向真实账号制造故障。

## alpha32 订阅查询

DeepSeek、OpenCode Go／Console 和 Cursor 的前台读取也使用同一重试策略，最多三次；各服务独立限流，认证与格式错误不自动重试，可取消进行中的请求。缓存五分钟，手动刷新仍遵守 Retry-After。具体凭据、接口与兼容边界见[订阅服务说明](SUBSCRIPTIONS.md)。

## alpha33 更新检查

发布流程仅在签名 APK 公开且摘要、版本、来源一致后，写入 `update-feed` 分支的 `updates.json`。客户端从 `raw.githubusercontent.com/tsonglew/Quodex/update-feed/updates.json` 读取索引，仅连接失败／超时时才尝试 GitHub REST Releases API，不因 HTTP 限流、格式错误、TLS 验证失败或取消而切换来源；APK 下载地址与完整性、包名、版本和签名校验保持原有规则。CDN 缓存或网络故障仍可能延迟发现新版本。

更新服务要求等待时，设置显示本机时区的具体重试时间，并暂时禁用检查按钮；界面时钟更新后恢复按钮。迁移时将旧 API 的截止时间移入备用来源设置，不阻塞新索引；两个来源的截止时间继续跨进程保存。备用来源受限时明确显示它的等待时间，主来源仍可重新检查。诊断记录检查结果、失败 HTTP 状态及等待截止时间，不记录响应正文。旧版诊断没有更新检查状态码，不能仅凭“服务端要求等待”断言是 429。

旧 APK 无法自行获得这一修复。如果仍被旧接口的等待状态阻塞，可从 GitHub Releases 下载实际已发布的 alpha33 或更高版本，以相同签名覆盖安装；无需卸载。不要使用 debug 包覆盖正式包。

## 重置卡明细（alpha34）

明细 GET 复用有限重试（最多三次），独立遵守 Retry-After；手动刷新不能绕过等待。界面显示重试时间，等待期间禁用刷新。五分钟缓存与十秒防连点降低重复请求，失败后自动检查至少间隔一分钟；错误和缓存不影响额度、Token 统计或其他订阅。只在展开明细的前台页面查询，不新增后台任务。
